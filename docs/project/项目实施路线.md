# KITTI + AB3DMOT 从 0 到 1 实施路线

版本：v1.1｜2026-11-10｜状态：阶段 0 基础盘点完成，待进入阶段 1

## 1. 目标和工作方式

以《项目需求文档.md》为验收依据：完成固定检测输入下的基线复现、错误分析、一项关联改进、受控鲁棒性实验和可复现报告。预计投入约 60 小时；这是规划预算，不保证在该时间内找到满足要求的改进。未达到科学验收标准时如实记录阶段成果并继续评估投入。

采用“讲清原理 → 给出少量操作 → 用户执行 → 检查输出 → 记录证据 → 进入下一步”的指导方式。每轮只处理一个可验证目标。命令必须标明在 Windows PowerShell 还是远程 Linux 中执行，并说明工作目录、目的、成功输出及常见失败分支。尚未核实的命令不得写成已验证流程。

## 2. 环境决策

- 主执行环境：已有 AutoDL Linux 服务器。先确认发行版、CPU、内存、磁盘、SSH 接入及存储持久性，再选择 Python 环境和版本。
- 本地 Windows 项目为准：维护文档、学习记录、脚本、配置及回收的关键结果。远程只负责脚本运行和验证，不要求维护 Markdown 文档。
- 本地 WSL2：可选后续项，不作为启动项目的前置条件。
- 本项目使用预计算检测，CPU 即可运行；不为本项目先配置 CUDA，也不训练或重新推理 PointRCNN。
- 正式结果指定唯一主环境。两端通过 Git 同步代码，通过清单同步输入和依赖，不复制整个虚拟环境。
- 核实 AutoDL 实例关机、释放及磁盘保留规则。重要代码、清单和小型实验结果及时备份；不默认服务器磁盘永久保留，不将原始 KITTI 数据提交 Git。

## 3. 阶段路线与预算

下列为主动工作时间估算，下载等待不计入；总计约 60 小时。

| 阶段 | 时间 | 动手任务 | 学习重点 | 验收证据 |
|---|---:|---|---|---|
| 0. 接入与盘点 | 2h | 连接服务器，识别系统、资源、持久化目录，建立项目目录 | SSH、绝对/相对路径、终端与工作目录 | 资源记录、目录说明、可重复连接 |
| 1. 锁定代码与依赖 | 4h | 获取官方代码并锁 SHA；核查依赖来源，建立隔离环境，解决旧依赖兼容 | Git、Python 环境、退出码、错误日志 | SHA、依赖记录、关键模块导入成功 |
| 2. 最小数据与冒烟运行 | 6h | 核查检测文件和 split 覆盖；准备一个验证序列的必要数据；核对路径、格式和帧索引；运行跟踪及评测 | KITTI schema、相机坐标、数据完整性 | 一个序列完整运行、输入清单和原始日志 |
| 3. 完整基线复现 | 8h | 准备完整验证数据；优先完成 Car，预算允许时完成三类；运行规定评测并复跑检查稳定性 | 指标、阈值扫描、版本匹配 | 基线表、计数、容差判断、可重复命令 |
| 4. 理解代码与诊断 | 8h | 阅读检测读取、状态预测、关联、轨迹管理和评测；分析逐序列错误；选择代表案例 | 卡尔曼滤波、关联代价、门控、轨迹生命周期 | 算法流程笔记、错误分类、可检验假设 |
| 5. 改进探索 | 12h | 在开发数据上实现一个可关闭的候选方案，记录探索与失败；比较参数并冻结方案 | 控制变量、消融、防泄漏 | 开发实验记录、补丁、关闭后恢复基线的证据 |
| 6. 正式鲁棒性实验 | 12h | 固定扰动生成器、清单和哈希；按需求运行 50 次主比较；补充消融、逐序列分析 | 成对比较、随机种子、统计解释 | 原始日志、完整结果 CSV、曲线及验收判断 |
| 7. 整理与复现 | 8h | 从日志生成表图；整理失败案例；验证复现入口；写报告并准备项目讲解 | 工程交付、科学表达、面试叙述 | README、环境及输入清单、报告、复现检查记录 |

说明：阶段 5 的开发探索、正式消融、基线重复运行不包含在需求规定的 50 次主比较内。先测单次跟踪和评测耗时，再估算阶段 6 的实际计算时间。若预算不足，首先删除可选可视化、点云、HOTA 和非必要扩展；不得删减必需实验后宣称完整验收。

## 4. 顺序和关卡

1. 没有确认持久化存储，不开始大规模下载。
2. 没有锁定代码和核实检测输入，不开始性能比较。
3. 没有跑通单序列跟踪与评测，不下载和排查全部数据。
4. 基线未通过复现判断，先定位版本、依赖、输入、路径和评测差异，不开始声称算法改进。
5. 在开发实验开始前锁定开发和留出划分；检测不覆盖开发池时，按需求预声明替代划分。
6. 先诊断错误，再选改进。路线不提前承诺某个算法一定有效。
7. 开发阶段冻结方法、参数、扰动规则和分数策略，再运行最终留出评测。不得根据留出结果反复调参而继续宣称独立检验。
8. clean sAMOTA 下降不超过 0.5 个百分点、扰动平均提升至少 0.5 个百分点，并满足消融等要求，才按需求判断科学验收通过。

## 5. Linux 学习嵌入项目

| 时机 | 要掌握的操作 | 完成标准 |
|---|---|---|
| 首次接入 | pwd、ls、cd、mkdir、文件查看、命令帮助 | 能解释当前目录和项目数据位置 |
| 安装依赖 | 环境激活、which、环境变量、权限基础、Git | 知道当前使用哪个 Python，能读懂安装失败日志 |
| 准备数据 | 下载、解压、磁盘检查、哈希、软链接 | 能发现磁盘不足或路径错误，避免维护多份数据 |
| 跑实验 | 输出重定向、管道、退出码、tmux、ps、top、kill | 断开 SSH 后任务继续，能找到日志并判断成功与失败 |
| 批量实验 | 简单 Shell 脚本、参数、循环、失败即停 | 能可靠启动批量运行，避免覆盖结果 |
| 交付 | Git diff、依赖及配置记录、复现脚本 | 能在新环境按说明重建并运行 |

不要求先系统学习 Linux 运维、内核、复杂网络或 Docker。需要时补充，不让工具学习挤占算法与实验预算。涉及删除文件、权限修改和进程终止时，先理解作用对象和影响。

## 6. 产物与记录

沿用现有目录：third_party/ 保存上游代码；src/ 放改进及薄适配；scripts/ 放运行入口；configs/、splits/ 放冻结配置和划分；manifests/ 放环境、输入和版本清单；runs/ 放不可覆盖的运行输出；reports/ 放报告与图；docs/ 放学习和决策记录。

每次实验记录需求规定的 run_id、UTC 时间、代码 SHA/dirty diff、输入哈希、配置、种子、命令、日志、耗时和原始评测输出。每轮指导记录“执行目标、操作、实际输出、结论、下一步”；密码、私钥和访问令牌不写入仓库或学习记录。

最终能够讲清：检测输入与跟踪器的边界、状态与坐标定义、关联失败机制、改进依据、数据划分、防泄漏措施、结果及限制，以及自己解决过的实际 Linux 和依赖问题。

## 7. 下一轮的具体起点

阶段 0 已完成基础盘点，详见 manifests/environment-stage0.md。下一步进入阶段 1：获取并锁定官方代码，先检查依赖再选择独立 Python 环境。当前无卡模式仅有 0.5 核 CPU 配额及 2GiB 内存；数据盘剩余约 35GB，系统盘剩余约 3.1GB。安装前需规划环境和缓存位置。

环境事实基于用户提供的终端输出及确认，助手未直接登录服务器。尚未检查上游锁定版本、验证依赖或运行基线。具体安装命令和候选改进将在相应关卡核实后确定。
